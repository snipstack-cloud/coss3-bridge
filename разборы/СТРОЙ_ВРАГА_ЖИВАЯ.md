# Ветка `idea/formation` на живой игре: тик цел, но строй читается не у того отряда

Проверено на Windows 25.09, партия 915 игровых секунд. Партию вёл
`march_by_hand` (водитель без модели), поэтому проверка не стоила денег.

## Что прошло

| проверка | результат |
|---|---|
| `verify_blocks` | чист, `begin/end` 113/113 |
| контрольные числа установки | **1593 / 1190 / 3155** — сошлись с песочницей мака до числа |
| пульс | **есть через 24 с**: тик `Progress` собрался с 31 новой строкой |
| поля отрядов в состоянии | есть с 4-й секунды: `p1_squads`, `p1_squad_units`, `p1_squad_hold` |
| счётчик не врёт нулём | **живой**: 1 → 2 → 5 отрядов, в крупнейшем 36 бойцов |
| команда `FORMATION` | отказывает вслух во всех ветвях (см. ниже) |

**Подозрение, которое НЕ подтвердилось.** `hsysqu` и `hsysqh` объявлены внутри
вложенного `begin` — это форма, которая 17.09 дала нули при 208 бойцах в сетке
(«массив копил верно, числа — нет»). Здесь она сработала верно: 36 бойцов в
крупнейшем отряде — число, недостижимое для мёртвого счётчика. Проверять всё
равно стоило: `verify_blocks` такого не ловит, а признак был назван заранее
(«`p1_squads > 0` при `p1_squad_units = 0`»), поэтому ответ вышел однозначным.

`FORMATION` проверена прямым вызовом `to_commands` на ЖИВОМ состоянии:

| случай | итог |
|---|---|
| живое состояние (офицеров 0, барабанщиков 0) | отказ вслух, с обоими числами и с тем, как починить |
| офицер и барабанщик есть | команда уходит в игру |
| офицер есть, барабанщика нет | отказ вслух |
| без состояния (старые вызовы) | уходит в блок, он откажет сам |

## Что НЕ прошло, и это надо править

**`p1_squad_form` / `_dmg` / `_def` не появились НИ РАЗУ за 915 секунд**, хотя
у врага к концу было 141 пехотинца, 4–5 отрядов и, по наблюдению игрока
глазами, ОФИЦЕР на поле.

Причина в самой правке, строки блока:

    if (TSquad(hsypsq).GetCount > hsysqu) then
    begin
       hsysqu := TSquad(hsypsq).GetCount;
       hsysqf := TSquad(hsypsq).fFormation;
    end;

**Строй берётся только у САМОГО КРУПНОГО отряда.** Что максимум отслеживается
верно, видно по `p1_squad_units = 36`; значит `hsysqf` читался именно у него и
там стояло `-1`. Офицерский отряд был меньше — и для модели стал невидим,
потому что поля пишутся под `if (hsysqf >= 0)`.

**Почему это важно, а не мелочь.** Правка делалась ради того, что калькулятор
боя переоценивал нас ВТРОЕ на 329 боях, и недостающее слагаемое — строй врага.
Но в типовой партии самый крупный отряд — безофицерская толпа пехоты, а строй
стоит у меньшего, офицерского. То есть поле молчит ровно в том случае, ради
которого заведено, и молчит НЕ как ошибка, а как задумано.

## Что предлагается маку

Читать строй не у крупнейшего отряда, а у того, у кого он есть. Варианты, по
возрастанию цены:

1. отдельный проход: первый отряд с `fFormation >= 0` — и его `sid`, `bonusdamage`,
   `bonusshield`;
2. лучше: число отрядов СО СТРОЕМ (`p<n>_squads_form`) и ЛУЧШИЙ бонус среди
   них — тогда видно и сколько его войска в строю, и насколько это больно;
3. заодно стоит решить, что делать с `p1_squad_hold`: за 915 с он был нулём
   всё время — враг ни разу не включил удержание, так что этот счётчик живой
   игрой НЕ проверен (в отличие от `_units`). Ноль здесь объясняется
   поведением врага, а не гейтом в коде.

Пока не поправлено — **ветка НЕ влита**. Тик она не роняет, но сливать её
смысла нет: поле в бою будет пустым.

## Ответ мака, 25.09 утро

Сделан вариант 2 из списка выше. Блок за один проход по отрядам считает всех,
крупнейшего и стоящих (как было), и отдельно отряды, у которых `fFormation >= 0`
и сумма четырёх бонусов больше нуля: их число `p<n>_squads_form`, сколько из них
в удержании `p<n>_squads_form_hold`, и лучший из них (больший бонус, при равном
— больший отряд): `p<n>_squad_form`, `_squad_form_units`, `_squad_dmg`, `_def`,
`_hdmg`, `_hdef`. Python читает поправку по `squads_form`, а не по `squads`, и
берёт бонусы из состояния, а не из констант: толпа из пяти безофицерских
отрядов теперь даёт «строя у врага нет», а один LINE15 из пяти — «+2/+2, у него
1 отряд в строю на ходу». Песочница 1619 / 1190 / 3181, `verify_blocks` чист,
63 самопроверки чисты, мок повторяет живую картину (три отряда, строй у одного).
Про `p1_squad_hold` согласен: он живой игрой не проверен, и теперь рядом с ним
`p1_squads_form_hold` — тот, что решает про +7/+7.

## Живая проверка ДОРАБОТКИ, 25.09 день (Windows)

Партия 1096 игровых секунд, водитель `march_by_hand`, без модели — проверка
снова ничего не стоила. Установлена ветка `idea/formation` на `64a880d`.

### Прошло

| проверка | результат |
|---|---|
| `verify_blocks block_hstate.inc` | чист, `begin/end` **115/115**, строк **1619** |
| контрольные числа | **1619 / 1190 / 3219** |
| `hsysqfn` в установленном `progress.inc` | 3 вхождения |
| пульс | есть, тик собрался целиком |
| поля отрядов врага | все пять с первых секунд, нулями при `p1_inf = 0` |
| **`p1_squads_form > 0`** | **да, на 1084-й секунде: 1 отряд из 6** |
| поля лучшего отряда | `SQUARE15`, 17 бойцов, `dmg 2 / def 2 / hdmg 7 / hdef 7` |
| python читает по состоянию | `поправка_на_строй` даёт `откуда='по состоянию'`, `почему='у него 1 отряд(ов) в строю на ходу'` |
| строки запроса | «СТРОЙ ВРАГА: +2 … (у него 1 отряд(ов) в строю на ходу)» и «его отрядов В СТРОЮ: 1 из 5, лучший — SQUARE15 на 17 бойцов (+2/+2 на ходу, +7/+7 стоя), стоят на месте: 0» |

**Доработка сделала ровно то, ради чего затевалась.** Крупнейший отряд снова
оказался безофицерским — 36 человек, `fFormation` -1, как и 25.09 утром. Строй
стоял у МЕНЬШЕГО, из 17 бойцов. Прежняя версия на этой же картине молчала бы.

**Число мака надо поправить: не 3181, а 3219.** 3181 посчитано до того, как в
`master` влилась скорость партии (`block_gameloop` 182 → 220); ветка её уже
содержит, и 3162 + 57 = 3219. Числа блоков — 1619 / 1190 — сошлись до единицы.

### Строй у одного отряда из шести, и это про плоскую поправку

`p1_squads_form = 1` при `p1_squads = 6`, и в строю 17 бойцов из 155 пехоты —
**11 %**. Поправка `+2/+2` при этом накладывается на ВСЮ его армию. Для подгонки
по 329 боям это законно: плоская поправка и калибровалась как среднее, а доля
отрядов в строю в тех партиях была примерно такой же. Но буквальным бонусом её
считать нельзя, и если когда-нибудь захочется масштабировать её по доле — сначала
придётся перекалибровать, иначе подгонка сломается.

### Не проверено живой игрой, и это надо знать

* **`p1_squad_hold` и `p1_squads_form_hold` — оба ноль всю партию.** Враг ни разу
  не включил удержание, так что ветка `+7/+7` живой игрой НЕ проверена. Это
  поведение врага, а не гейт в коде: рядом стоящие поля того же прохода живые.
* **Наш собственный `FORMATION` не проверен в этой партии.** В ней у нас 0
  бойцов, 0 офицеров, дерева 270 — академию не поставить, строить некому:
  `march_by_hand` только водит, билд-ордер не работал. Блок `block_hcmd.inc`
  ветка не менялa (команда там с 16.09 и живой игрой проверена), отказы
  `to_commands` проверены прямым вызовом 25.09 утром, но УДАЧНЫЙ путь
  «академия → офицер + барабанщик → `FORMATION` → `squads` 1» глазами не видели.
* Строка «его отрядов В СТРОЮ» загорожена `if _своих:` вместе со всем блоком
  «твоя сила» — без своих бойцов её не будет. Проверена подстановкой `mil_inf`
  в живое состояние; в настоящей партии под моделью армия есть всегда, так что
  это не дыра, но знать стоит.
