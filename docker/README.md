# Десять копий Cossacks 3 в контейнерах

Собирается на маке, работает на сервере x86_64 Linux. Один контейнер — одна
копия игры со своим мостом и своей моделью.

## Почему без Windows

Просили «докер с виндой, внутри игра». На сервере это не нужно, и вот почему.

`cossacks.exe` — 32-битное приложение Windows (проверено по заголовку PE,
`machine = 0x14c`). На **x86_64 Linux его исполняет Wine напрямую, без эмуляции
процессора**: команды те же, эмулируется только слой Windows API. Графика идёт
через DXVK, который переводит Direct3D 9 в Vulkan — и это не гипотеза: в папке
игры лежит `cossacks_d3d9.log` от попытки под Wine, где DXVK 1.10.3 опознал
`cossacks.exe` и устройство. Отдельно: Cossacks 3 числится рабочей на
[ProtonDB](https://www.protondb.com/app/333420) под GE-Proton.

Разница на десяти копиях:

| | Windows в контейнере | Wine (этот образ) |
|---|---|---|
| на копию | ~4 ГБ RAM, ~40 ГБ диска, отдельная виртуальная машина | ~1,5 ГБ RAM, тонкий слой поверх общего образа |
| десять копий | ~40 ГБ RAM, 400+ ГБ диска | ~15 ГБ RAM, игра лежит **один раз** |
| видеокарта | одну карту на десять VM не поделить | десять процессов делят её свободно |
| старт копии | загрузка Windows, минуты | секунды |
| лицензии Windows | десять | ноль |

Игра запечена в образ нарочно: слои Docker общие, поэтому десять контейнеров из
одного образа делят одни и те же 8 ГБ, а каждый пишет только свою разницу. Мост
патчит 6 МБ скриптов — они уедут в верхний слой копированием-на-запись.

**На Apple Silicon этот образ не запускается и не должен.** Там нет x86-KVM, и
Wine из «исполняет напрямую» превращается в «эмулирует», то есть теряет весь
смысл. Мак — сборочная машина: `docker buildx` под `linux/amd64` собирает образ,
не запуская его.

## Собрать и перенести

```bash
./docker/build.sh                             # собрать локально
./docker/build.sh --ship user@server          # собрать и залить по ssh
./docker/build.sh --push reg.example/coss3:1  # через реестр (быстрее при повторах)
```

`--ship` гонит `docker save | zstd | ssh 'zstd -d | docker load'` — образ нигде
не ложится на диск целиком.

**Три разных числа про размер, и путать их дорого:**

| | сколько | где важно |
|---|---|---|
| контент образа | **3,85 ГБ** (`docker image inspect`) | столько передаётся по сети, минус сжатие zstd |
| распакованный на диске | **~10 ГБ** внутри контейнера, до 14,5 ГБ со снапшотом | **столько нужно диска на сервере** |
| десять контейнеров | те же ~10 ГБ | слои образа общие, каждая копия добавляет только свою разницу |

`docker images` показывает третье число (14,5 ГБ) и этим путает: на сервере
надо смотреть на диск под распакованный образ, а на канал — на 3,85 ГБ.

Путь к игре переопределяется `COSS3_GAME_SRC`, тег — `COSS3_TAG`.

## Запустить десять копий

```bash
cp docker/coss3.env.example docker/coss3.env   # вписать ключ модели
docker compose -f docker/compose.yaml up -d
docker compose -f docker/compose.yaml logs -f coss3-0
```

Трассы и логи каждой копии — в `docker/io/<номер>/`:
`coss3_bot.jsonl` (трасса для обучения), `coss3_llm.log`, `game.log`,
`install.log`. Разбор — как обычно:

```bash
python3 log_review.py --trace docker/io/3/coss3_bot.jsonl
```

## Поставка игры: только GOG, и это не вкусовщина

**В образ годится только копия GOG (Digital Deluxe). Стимовская — нет.**
Стимовская завязана на клиент Steam, а в контейнере его нет и не будет.
GOG-версия свободна от DRM, и именно на этом вся затея с образом и держится.

Собранный образ содержит правильную: `galaxy.dll` есть, `steam_api.dll` нет
вовсе (проверено внутри образа). Источник — GOG-копия с мака.

`build.sh` теперь отказывается собирать из стимовской папки: увидел
`steam_api.dll` — остановился и сказал почему. Отсутствие `galaxy.dll` —
предупреждение, а не отказ.

Практическое следствие: **на Windows образ пересобирать НЕЛЬЗЯ**, если там
стоит Steam-версия. Нужно переносить готовый.

## Запуск на Windows через WSL2 — ПРОВЕРЕНО 13.09

Сервер для этого не нужен: Windows-машина x86_64, а Docker Desktop с бэкендом
WSL2 — настоящий Linux на том же процессоре, без эмуляции.

**Переносится образ, а не игра.** Он ~3,9 ГБ, меньше самой папки игры (9,4 ГБ),
и в нём уже нужная GOG-поставка.

```bash
# на маке
docker save coss3:1 -o ~/coss3.tar

# на Windows, в Ubuntu (WSL)
docker load -i /mnt/c/Users/<вы>/coss3.tar
cd ~ && mkdir -p io profile
docker run -d --name coss3 --env-file coss3.env \
    -e COSS3_BRIDGE_GIT=git@github.com:snipstack-cloud/coss3-bridge.git \
    -v "$PWD/io:/io" -v "$PWD/profile:/profile" \
    -v ~/.ssh/coss3_deploy:/ssh/deploy_key:ro coss3:2
docker logs -f coss3
```

Четыре вехи в логе, каждая отвечает на свой вопрос:

```
мост обновлён: <SHA>                какая версия моста играет
пульс есть: тик Progress жив        собрался ли тик в игре
партия идёт: coss3_eco_P0.dat       есть ли человеческий игрок
условия: nat0 = 13, ai1 = 3, ...    те ли условия
запускаю модель: ...                дальше идут решения
```

Первую партию заводить руками НЕ нужно: контейнер сам шлёт `NEW` с условиями из
`COSS3_MATCH_*`.

### Конец партии: контейнер остаётся жив

До 13.09 последней строкой входного скрипта стоял `exec python3 llm_policy.py` —
политика становилась PID 1, и как только партия кончалась, контейнер
останавливался. Логи боя после этого не прочитать ничем:

```
docker exec coss3 python3 /opt/bridge/log_review.py --trace /io/coss3_bot.jsonl
Error response from daemon: container ... is not running
```

Теперь политика — обычный процесс. После неё контейнер:

* пишет разбор трассы в `/io/report.txt` и показывает его хвост в логе;
* кладёт рядом `/io/ack_last.dat` (квитанция последней команды) и
  `/io/policy.rc` (код возврата: 0 — цель взята, 2 — партия прошла без цели);
* остаётся стоять, пока его не погасят.

```bash
docker exec coss3 cat /io/report.txt
docker exec coss3 python3 /opt/bridge/log_review.py --trace /io/coss3_bot.jsonl --ideas
```

Выключается это `COSS3_KEEP_ALIVE=0`. Сколько партий играть подряд —
`COSS3_EPISODES` (по умолчанию 1); после каждой мост сам шлёт `NEW`, и это
работает даже с экрана поражения, потому что команду там берёт блок конца партии
в интерфейсе — в `Progress` она бы не дошла, симуляция стоит на паузе.

**Трасса лежит на томе, а не в контейнере.** Даже если контейнер всё-таки
остановился, `./io/<номер>/coss3_bot.jsonl` читается с хоста напрямую — нужен
только `log_review.py` из репозитория.

### Чего в контейнере НЕ работает: картинка

**Игра считает, но не рисует.** Двухмерный интерфейс (выбор профиля) рисуется,
трёхмерная сцена — нет, одинаково через OpenGL и через Vulkan. Ферме это не
мешает: модель играет по файлам, партия начинается командой. Мешает только
настроить что-то глазами — но и это теперь делается командой.

Что перепробовано и не помогло: программный растеризатор (`llvmpipe`, OpenGL 4.5
исправен — `glxinfo` подтверждает), виртуальный рабочий стол Wine, DXVK на
Vulkan 1.3, проброс видеокарты через `/dev/dxg` и Mesa `d3d12` (карта
подхватилась — `D3D12 (AMD Radeon)`, `Accelerated: yes`, — но игра стала падать
с прежним page fault, потому что `LD_LIBRARY_PATH=/usr/lib/wsl/lib` перекрыл
системные библиотеки).

Как посмотреть, что на экране, не подключаясь VNC:

```bash
docker exec coss3 sh -c 'DISPLAY=:99 import -window root /io/screen.png; ls -l /io/screen.png'
```

**Вес снимка и есть ответ**: пара сотен байт — сплошная заливка, десятки
килобайт — есть картинка. Этим мы и отличили чёрный экран от живого.

### Семь причин, по которым контейнер не запускался

Все сняты, все были молчаливыми. Держу список: каждая выглядела как «не
работает» и ни одна не говорила, почему.

| причина | как проявлялась |
|---|---|
| нет `xdpyinfo` (`x11-utils`) | проверка объявляла РАБОТАЮЩИЙ Xvfb сломанным |
| нет `/tmp/.X11-unix` | Xvfb не поднимался |
| диалог Wine Mono | `wineboot` ждал нажатия на невидимом экране |
| нет `libGL.so.1`, `libEGL.so.1` (i386) | **игра падала** с page fault до графики |
| замок `.X99-lock` из слоя образа | «Server is already active» при отсутствии сервера |
| Xvfb без `+extension GLX` | окно есть, OpenGL не рисует, снимок 212 байт |
| пульс путали с партией | пульс идёт и в меню, модель стартовала в пустоту |

## Ферма опытов: мастер на Windows, проверки на сервере

Разделение труда такое:

* **Windows — мастер-мост.** Там он правится и отлаживается на живой игре.
  Медленно, но по-настоящему: одна партия за раз, зато видно глазами.
* **Сервер — проверка идей.** Сюда приезжает уже проверенная на мастере версия,
  десять копий дают десять партий разом. Мастер при этом не простаивает.

**Мост едет из git, а не запекается в образ.** Иначе правка одного `.py`
означала бы пересборку и перегон 3,85 ГБ. Образ держит то, что не меняется
(игру, Wine, DXVK), а мост берёт при старте:

```bash
export COSS3_BRIDGE_GIT=git@github.com:snipstack-cloud/coss3-bridge.git
./docker/exp.py run wave40
```

### Доступ к приватному репозиторию: deploy key

Ключ создан и добавлен на GitHub **только на чтение**:

```bash
ssh-keygen -t ed25519 -f ~/.ssh/coss3_deploy -N ''
gh repo deploy-key add ~/.ssh/coss3_deploy.pub --title "сервер опытов (только чтение)"
```

`exp.py` монтирует его в контейнер сам (`-v ~/.ssh/coss3_deploy:/ssh/deploy_key:ro`),
путь переопределяется `COSS3_DEPLOY_KEY`. На сервер ключ копируется отдельно —
`scp ~/.ssh/coss3_deploy user@server:~/.ssh/`, права 600.

Почему именно так, а не токеном в переменной окружения:

* **ключ не попадает в образ.** Слой с ключом остался бы в истории образа
  навсегда, и его достал бы любой, у кого образ есть. Монтирование такого следа
  не оставляет;
* **токен виден в `docker inspect` и в списке процессов**, ключ — нет;
* **deploy key только на чтение и только на этот репозиторий.** Утёк — меняется
  одной командой, и больше ничего не задето.

**Проверка подлинности хоста НЕ отключена.** `StrictHostKeyChecking=yes`, ключи
хоста `github.com` вшиты в образ и при сборке сверены с отпечатками, которые
GitHub публикует. Если GitHub их сменит (так было в 2023 с RSA), сборка упадёт —
и это правильно: молча взять новый ключ хоста значит согласиться на подмену
того, откуда берётся код, который потом правит файлы игры.

`IdentitiesOnly=yes` тоже не украшение: без него ssh переберёт все ключи агента,
GitHub ответит на первый подошедший, и контейнер пойдёт не тем ключом, каким вы
думаете.

Контейнер клонирует репозиторий, переключается на нужный ref и **печатает
точный SHA, а также кладёт его в `/io/bridge.sha`**. Это не формальность: через
неделю по трассе без версии моста не сказать, что именно проверялось, и вся
ферма превращается в набор несравнимых наблюдений. По той же причине при
неудаче клонирования контейнер НЕ откатывается на запечённую копию, а падает:
опыт над неизвестной версией хуже, чем отсутствие опыта.

Запечённая копия моста в образе остаётся, но только для проверки самого образа
без репозитория — `exp.py` про это предупреждает и требует `--force`.

### Идея = ветка плюс флаги

Идеи живут в `docker/experiments.ini`, правятся руками:

```ini
[wave40]
что = порог волны 40 вместо 20 — бить реже, но вдвое большей силой
ref = master
флаги = --wave-min 40
копий = 10
база = baseline
```

Идея, которая живёт во флаге, не требует ничего, кроме строки здесь. Идея,
которая требует правки кода, делается веткой на мастере: `ref = idea/formations`
— и образ пересобирать не нужно.

### Консоль

```bash
./docker/exp.py list             # какие есть идеи
./docker/exp.py run wave40       # поднять (число копий из ini)
./docker/exp.py run wave40 --copies 1   # сначала одна, как и задумано
./docker/exp.py status           # кто жив, сколько тактов, игровое время
./docker/exp.py report wave40    # свод и сравнение с базой
./docker/exp.py stop wave40
```

`report` печатает по копии на строку — такты, игровое время, своих крестьян,
армию, **крестьян врага «было → стало»**, сколько убито, сколько волн ушло,
брак команд, сколько волн отверг мост, и SHA моста. Потом среднее, «цель взята
в N копиях из M» и разницу с базой по каждому показателю.

Порядок работы ровно тот, что вы описали: сначала `--copies 1` — убедиться, что
идея вообще запускается и партия идёт; потом полные десять.

## Какой сервер брать (DigitalOcean, цены на 12.09.2026)

### Для первой проверки образа

**CPU-Optimized 4 vCPU / 8 ГБ / 50 ГБ — $0,125 в час.** Создать, проверить,
удалить: два часа стоят четверть доллара.

Почему именно так:

* **не Basic.** Shared CPU троттлится на постоянной нагрузке, и вы получите
  «игра тормозит» там, где виноват не образ, а тариф;
* **не 2 vCPU за $42/мес.** Диска там 25 ГБ — впритык под образ (~10-15 ГБ
  распакованного) плюс система. И если рендер на процессоре захочет два ядра,
  на двухъядерной машине замер соврёт в худшую сторону;
* **4 ядра и 50 ГБ** дают честный замер и запас, чтобы отличить «образ сломан»
  от «сервер мал».

Дальше — по выводу `measure.sh`, а не по догадке.



**Сначала то, что брать НЕЛЬЗЯ: Basic, он же shared CPU.** Даже старший план за
$96/мес (8 vCPU, 16 ГБ) DigitalOcean прямо называет «для приложений с
переменной нагрузкой» — на постоянных 100% такие троттлятся. У нас нагрузка
ровно постоянная. Нужны выделенные ядра.

| план | vCPU | RAM | диск | $/мес | когда подходит |
|---|---|---|---|---|---|
| CPU-Optimized | 8 | 16 ГБ | 100 | $168 | только если копия ест <0,8 ядра; памяти впритык |
| CPU-Optimized | 16 | 32 ГБ | 200 | **$336** | базовый расчёт: ~1,5 ядра на копию |
| CPU-Optimized | 32 | 64 ГБ | 400 | $672 | с запасом, 3 ядра на копию |
| General Purpose | 16 | 64 ГБ | 200 | $504 | если упрёмся в память, а не в ядра |
| **GPU: RTX 4000 Ada** | 8 | 32 ГБ | 500 | ~$555 ($0,76/ч) | рендерит видеокарта, ядра почти не нужны |

Памяти на десять копий надо ~17 ГБ, диска — 12 ГБ под образ. По этим двум
меркам подходит почти всё. **Решают ядра**, а их потребление целиком зависит от
того, сколько CPU съедает программный растеризатор.

**И здесь неочевидное: GPU-дроплет может выйти ДЕШЕВЛЕ в пересчёте на партию.**
Считается так (числа ниже — прогон `measure.sh` на выдуманных входах, не замер):

| | скорость игры | партий в час с 10 копий | нужен план | $ за партию |
|---|---|---|---|---|
| софт-рендер | 0,2x | ~8 | CPU-Opt 16/32, $336 | $0,058 |
| как на Windows-машине | 1,38x | ~55 | CPU-Opt 32/64, $672 | $0,017 |

Семикратная разница в пропускной способности перекрывает двукратную разницу в
цене. Но обе строки — арифметика на догадках, и ставить на них $500 в месяц
нельзя.

## Померить, а не гадать

```bash
./docker/measure.sh            # 120 секунд замера
./docker/measure.sh 300        # дольше и точнее
```

Скрипт поднимает ОДНУ копию (модель выключена, ключ не нужен), ждёт, пока вы
начнёте бой через VNC, и меряет две вещи: **скорость игрового времени** и
**сколько ядер ест копия**. Из них считает, сколько копий влезет, сколько
партий в час выйдет и какой дроплет брать — с ценой за партию по каждому плану.

Замер на самом дешёвом выделенном дроплете (CPU-Optimized 2 vCPU, $0,0625/час)
стоит **тринадцать центов** и занимает двадцать минут. Это единственный честный
способ выбрать между $336 и $555 в месяц.

Если скорость окажется сильно ниже 1,0 — повторить тот же замер на
GPU-дроплете: там `/dev/dri` есть, `measure.sh` пробросит его сам и скажет
разницу числами.

## Сколько копий влезет

Считать по замеру, а не по этой таблице — но порядок такой:

* **память:** ~1,5 ГБ на копию (Wine + игра + питон). Десять — около 15 ГБ,
  плюс запас системе. На 32 ГБ сервере десять копий живут, на 16 ГБ — пять.
* **процессор:** с видеокартой копия ест меньше ядра. **Без карты** весь
  Direct3D считает процессор (lavapipe), и копия съедает 1–2 ядра целиком.
  Десять копий без карты — это 10–20 ядер, и именно здесь всё упрётся.
* **диск:** ~10-15 ГБ под образ, один на всех, плюс мелочь на копию. Даже
  младший CPU-Optimized (100 ГБ) с запасом.

Уменьшить нагрузку без карты: `COSS3_RES=640x480` в `coss3.env`.

Проверить, что видит контейнер:

```bash
docker compose -f docker/compose.yaml exec coss3-0 vulkaninfo --summary | head
```

Контейнер и сам говорит об этом при старте — если растеризатор программный, в
логе будет «ВНИМАНИЕ: это ПРОГРАММНЫЙ растеризатор, видеокарты у контейнера
нет». Молчаливого отката тут нет по правилу №1 проекта.

## Чего образ ещё НЕ умеет: завести первый бой

Честно и крупно, потому что это единственное место, где автоматизация не
дописана. Мост живёт в тике `Progress`, а тик работает только **в бою**. Пока
игра стоит в главном меню, ни пульса, ни состояния нет, и контейнер скажет
«ПУЛЬСА НЕТ» — это не поломка, это меню.

Петля эпизодов умеет команду `NEW` (`GUIExecuteState('DoNewGame')`), то есть
ВТОРУЮ и последующие партии контейнер начинает сам. Проблема ровно в первой.

Что с этим делать сейчас: поднять копию с `COSS3_VNC=1`, подключиться на
`localhost:5900` и начать бой руками — свой слот ЧЕЛОВЕК, советник ВЫКЛЮЧЕН,
противник компьютер, настройки `1к 0пт, без рынка, без дипа, без пушек`.
Дальше партии идут сами.

Что стоит сделать потом, по убыванию надёжности:

1. **Сохранёнка.** Начать бой один раз, сохранить, положить сейв в образ и
   загружать его на старте. Надо проверить, умеет ли `cossacks.exe` принимать
   сейв параметром командной строки — в проекте это не выяснено.
2. **Клики по меню** через `xdotool` (он уже в образе): координаты пунктов на
   фиксированном разрешении не плавают.
3. **Свой блок в меню.** `menu.inc/doprogress.inc` — такой же скрипт, и
   `PROGRESS.md` §10 уже разбирал, как в него врезаться. Самый чистый путь и
   самый долгий.

## Что проверено, а что нет

Проверено: образ собирается под `linux/amd64` (Wine с i386-слоем, DXVK, все
8,3 ГБ игры); в образе нет ключей API — `.dockerignore` не пускает
`nim_key.txt` даже в контекст сборки, и это подтверждено отдельной сборкой;
игра в образе ЧИСТАЯ — `clean_game.py` снимает старую компьютерную ветку моста
и валит сборку, если следы `BRIDGE` остались; `docker compose config`
разворачивает окружение во все десять служб.

**Установка моста проверена по-настоящему**, на песочнице из настоящих скриптов
игры на этом маке: `verify_blocks.py` дал 72/275/594 ОК, установщик — **1119
строк** и «проверка после записи: все блоки на месте». Это ровно контрольное
число из `RESUME.md`, то есть человеческий слот встаёт на POSIX-путях так же,
как на Windows. Это была самая рискованная часть `entrypoint.sh`, и она
закрыта.

**НЕ ПРОВЕРЕНО: игра под Wine в этом контейнере не запускалась ни разу.**
Проверить это на маке физически нельзя — нужен x86_64 Linux. Первый запуск на
сервере и есть проверка, и смотреть там надо по порядку: `game.log` (стартовал
ли Wine), пульс `coss3_hb.dat` (собрался ли тик `Progress`), затем
`coss3_eco_P*.dat` (пишется ли состояние).

**Отдельно про сборку на Apple Silicon.** Один шаг образа на маке не проходит и
не должен: создание префикса Wine. Под эмуляцией x86 **Xvfb зависает** —
процесс жив, экран не отвечает (ждал 60 секунд, вывод Xvfb пуст). На родном
x86_64 хосте этого нет. Поэтому шаг сделан необязательным: не вышло при сборке
— контейнер создаёт префикс при первом старте, и оба пути говорят о себе в лог.
Цена — 20–30 секунд на первый запуск каждого контейнера. Если собирать образ
на самом сервере, префикс запечётся и этой платы не будет.

**Что НЕ едет в образ и почему.** Папка игры за годы стала свалкой, и первая
редакция `Dockerfile` утащила из неё лишнего:

| | размер | что это |
|---|---|---|
| `cosaks222` | 1,0 ГБ | **чужой репозиторий** `hermes-agent`. Скрипты игры не ссылаются на него ни разу |
| `DLC` | 257 МБ | установщики GOG (`.exe`), а не контент — сам контент уже в `data/` и `dlcs/` |
| `Бонусные материалы` | 842 МБ | обои и саундтрек |
| `__redist` | 100 МБ | установщик DirectX, под Wine не нужен |
| `agency-agents` | 8 МБ | ещё один чужой репозиторий |
| `tmp`, `extracted` | 99 МБ | мусор прошлых распаковок |

Итого 2,3 ГБ, которые уехали бы на сервер без пользы. Первые две строки поймал
полный скан уже СОБРАННОГО образа — тот самый, что искал в нём ключи API.

Грабли, на которых я споткнулся, пока это писал, — все теперь в коде
комментариями:

* **bash не допускает кириллицу в именах переменных** (Python допускает, и в
  проекте они есть). `ИГРА=...` он принимает за команду, причём `bash -n` этого
  не ловит — падает только в рантайме.
* **`$VAR` перед не-ASCII символом** затягивает его первый байт в имя
  переменной: `«$GAME_SRC»` превратилось в `GAME_SRC»`. Лечится скобками:
  `${GAME_SRC}`.
* **проверка, которая не могла провалиться.** После установки моста
  `entrypoint.sh` сравнивал число строк `progress.inc` с 248 — и не сработал бы
  никогда: установщик печатает «1119», считая через `split("\r\n")` (хвостовой
  пустой элемент), а `splitlines()` даёт 1118. Числа в документации сдвинуты на
  ту же единицу. Переписано на метки блоков, они от способа счёта не зависят;
  проверено в обе стороны — на чистой игре код 1, после установки код 0.
* **проверка на секреты смотрела уже своей области, чем риск.** Она сканировала
  `/opt/bridge` — наши файлы — и прошла бы мимо чужого репозитория, приехавшего
  ВНУТРИ папки игры (а он там был, с ключеподобными строками в документации;
  к счастью, плейсхолдерами вида `sk-or-v1-your-key`, а не настоящими).
  Теперь сканируется весь `/opt`, кроме `data/` — там 6,9 ГБ бинарных ассетов,
  где секретам взяться неоткуда.
* **ключ слияния YAML не сливает вложенные карты, а заменяет их.** В первой
  редакции `compose.yaml` у каждой службы был свой `environment` с номером
  копии — и он стирал из якоря модель, ключ и такт. Поймано `docker compose
  config`. Теперь номер копии берётся из имени хоста, а `environment` живёт в
  одном месте.
