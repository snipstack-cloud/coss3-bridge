# Тест контейнера НА MAC

Это скилл ПРОВЕРКИ: заводится ли копия игры на этой машине и играет ли модель.
Не серия опытов и не сравнение идей — для этого `coss3-farm`.

## СТОП, прежде чем что-либо делать

**Только macOS.** Первым делом:

```bash
uname   # должно быть Darwin
```

Не `Darwin` — **немедленно остановиться и сказать об этом**. На Windows ферма
работает иначе (WSL2, без Colima), и там действует `coss3-farm`. Команды отсюда
на Windows не годятся ни одной строкой.

**Не путать скиллы:**

| | |
|---|---|
| **этот** | Mac, Colima x86_64, проверка «заводится ли» |
| `coss3-farm` | сервер и Windows, серия идей ради сравнения |
| `coss3-results` | разбор того, что прогон принёс |
| `coss3-human-bot` | правка моста; на Mac её **не проверяют** — только на Windows |

## Шаг 1. Спросить человека ДО запуска

Два вопроса, ответы получить **до** первой команды `docker run`:

1. **Сколько эпизодов** в каждом контейнере (партий подряд). Одна партия — это
   900 игровых секунд, то есть ~16 реальных минут.
2. **Сколько контейнеров** поднять (копий игры).

Сказать вслух цену, чтобы человек выбирал зряче:

* одна копия занимает **~370% CPU**, а в VM по умолчанию 6 ядер;
* памяти одна копия держит **1,5 ГиБ** на пике (замер 18.09), VM по
  умолчанию 6 ГБ; хосту нужнее — при забитых браузерах macOS снимает
  сторожей прогона, а не контейнер;
* при одной копии темп **1,00 игровой секунды на реальную** — как на железе;
* две копии VM ещё тянет, дальше темп проседает, и партии растягиваются;
* время ≈ `эпизоды × 16 минут` (плюс ~7 минут на загрузку игры в первый раз).

Больше двух копий — сначала поднять VM крупнее (`--cpu 10 --memory 16`), иначе
проверка померяет не игру, а нехватку ядер.

## Шаг 2. Запуск — только в фоне

Скрипт рядом делает всё: поднимает VM, если её нет, перегоняет образ, если его
нет в контексте Colima, заводит копии и следит за ними.

```bash
bash ~/.claude/skills/coss3-mac-test/mac_test.sh   # копия скрипта: ~/coss3-bridge/mac_test.sh <эпизодов> <копий>
```

**Запускать через Bash с `run_in_background: true`** — иначе сессия встанет на
часы. Проверить готовность, ничего не запуская: `mac_test.sh --check`.

Пока скрипт идёт, его лог смотреть так:

```bash
tail -20 ~/io-mac-runner.log      # что делает скрипт
docker --context colima-x86 logs --tail 20 coss3-mac-1
```

## Шаг 3. Четыре строки, по которым видно, что идёт задуманное

```
[firstrun] префикс готов               Wine жив (на Docker Desktop он тут падает)
пульс есть: тик Progress жив           блоки скомпилировались
партия идёт: coss3_eco_P0.dat          человеческий игрок на месте
0:20  <фраза модели>                   модель играет, а не молчит
```

Нет четвёртой строки, а первые три есть — смотреть ключ в `~/coss3.env`.

Темп мерить так (должно быть около 1,00):

```bash
docker --context colima-x86 exec coss3-mac-1 \
  grep -o 'gametime = [0-9]*' /opt/cossacks/coss3_hb.dat
```

Два замера с паузой в 60 секунд: разница должна быть около 60.

## Шаг 4. Итог

```bash
cat ~/io-mac-1/отчёт.md
```

Что считать успехом ПРОВЕРКИ: партия дошла до конца (исход назван — «горизонт»,
победа или поражение), отвергнутых команд 0, темп около 1,00. **Взятая цель
успехом проверки не является и не требуется** — она берётся примерно в одной
партии из пяти-десяти, и на Mac это ровно так же.

Гасить:

```bash
docker --context colima-x86 rm -f $(docker --context colima-x86 ps -aq --filter name=coss3-mac)
colima stop x86        # VM целиком, если Mac нужен под другое
```

## Что на Mac иначе, чем на сервере

* **Docker Desktop не годится вовсе.** x86 там эмулируется qemu-user, и Wine
  падает на `anon_mmap_fixed: Assertion !((UINT_PTR)start & host_page_mask)` —
  одинаково с win32 и win64 префиксом. Rosetta не спасает: 32-битный x86 она не
  умеет, а `cossacks.exe` 32-битный. Нужна VM с настоящим ядром x86_64.
* **Профиль игры обязателен.** Без тома `/profile` игра встаёт на «Cossacks 3
  configuration utility». Эталон лежит в `~/profile-mac`; если его нет, скрипт
  скажет об этом и даст порядок восстановления.
* **Загрузка игры ~7 минут**, поэтому `COSS3_HB_TIMEOUT=900` и
  `COSS3_NEW_TIMEOUT=600`. Штатных 90 секунд не хватает, и прогон был бы
  объявлен провалившимся на ровном месте. Замер 17.09: карта поднималась
  **255 секунд**, так что прежние 300 давали запас всего в 45 — а прогон
  `critic_forward` того же дня умер ровно здесь, на пределе 240 в
  `--new-timeout` (это ДРУГОЙ предел: он ждёт каждую следующую партию в
  петле эпизодов, и его значение по умолчанию тоже поднято до 600).
* **Экран в бою чёрный** (снимок ~212 байт) — это норма, модель играет по
  файлам. В меню картинка есть (~99 КБ).

## Короткая партия

Штатный горизонт — 900 игровых секунд. Нужна проверка покороче (например, семь
минут) — передать флаг переменной окружения, скрипт её пробросит:

```bash
COSS3_EXTRA_FLAGS="--horizon 420" bash ~/.claude/skills/coss3-mac-test/mac_test.sh   # копия скрипта: ~/coss3-bridge/mac_test.sh 1 1
```

Партия при этом доходит до конца и отчёт пишется — в отличие от простого «погасить
через семь минут», когда исход не назван и сравнивать нечего.

## Проверить свою правку python

Контейнер играет мостом, запечённым в образ. Чтобы проверить правку `.py`, не
пересобирая 14 ГБ, подложить местные файлы:

```bash
COSS3_BRIDGE_LOCAL=1 COSS3_EXTRA_FLAGS="--horizon 420" \
  bash ~/.claude/skills/coss3-mac-test/mac_test.sh   # копия скрипта: ~/coss3-bridge/mac_test.sh 2 1
```

Подкладываются `llm_policy.py`, `coss3_bridge.py`, `run_episodes.py` и все
`block_*.inc`. Два эпизода нужны всему, что связано с ПЕРЕХОДОМ между партиями.

**Что `.inc` тут проверяется, а что нет.** Контейнер ставит блоки в игру при
старте, поэтому строка «пульс есть» означает ровно одно: тик `Progress`
СОБРАЛСЯ вместе с вашим блоком. Это то, чего не знает `verify_blocks`. А вот
поведение блока — верны ли числа, те ли роли посчитаны — смотреть по состоянию
и трассе, и на Windows это быстрее: там цикл тридцать секунд, здесь семь минут
на загрузку игры.
