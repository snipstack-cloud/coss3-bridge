## 3. Как устроена игра (то, что нужно знать)

### Скрипты — это текст, а не бинарь

`.aix` — манифесты, перечисляющие состояния и указывающие на `.inc` с кодом
на встроенном Pascal-подобном языке (DmScript). Движок читает их при запуске.
Правка текста = мод. Перекомпиляция не нужна, инжект DLL не нужен.

### API движка задокументирован внутри exe

Сигнатуры лежат строками прямо в `cossacks.exe` — **4858 штук**:

```bash
strings -a cossacks.exe | grep -E "^\s*(procedure|function) "
```

Важное для моста: `ParserCreate`, `ParserSetIntValueByKeyByHandle`,
`ParserSaveToFileByHandle`, `ParserLoadFromFileByHandle`, `IsFileExists`,
`DeleteFileStream`, `Log`. Плюс `HTTPGetPars` — синхронный HTTP GET с разбором
ответа в структуру, если когда-нибудь понадобится канал быстрее файлов.

### Слой ИИ

| Файл | Строк | Роль |
|---|---|---|
| `units/global.inc/progressai.inc` | 17 | Диспетчер — движок зовёт его на каждого игрока |
| `units/global.inc/progresseconomicai.inc` | 4042 | Экономический мозг, 74 функции |
| `units/global.inc/progresswarai.inc` | 4261 | Военный мозг |
| `lib/ai.script` | 2530 | Общая библиотека ИИ (разведка, армии, зоны) |

Диспетчер троттлится константой движка `gc_global_TimeProgressAI`, игроки
разнесены по фазе (`plInd*0.25`). Это и есть готовый `step()` для бота.

### Модель принятия решений — декларативная

ИИ не строит напрямую. Каждый тик он заново объявляет желаемое состояние:

```
_ai_TryUnit(plind, cid, роль, желаемое_количество)   ← 141 вызов по файлу
      ↓  если хватает ресурсов И (есть + в работе) < желаемого
  aidata.bestprojects.Add → TAiIdea
      ↓
_ai_ProcessIdeas(plind)  → стройка / производство, очередь очищается
```

Идемпотентно: `_ai_TryUnit(..., ba17, 8, False)` значит «хочу всего 8 казарм»,
а не «построй 8 казарм». Повторный вызов ничего не ломает. **Мост построен
на той же семантике — это принципиально.**

### Билд-ордер, зашитый разработчиками

Из `_ai_BuildHouses` (эпоха «дерева», европейская нация):

```
1.  мельница ×1                    7.  кузница ×1
2.  ратуша ×1, затем ×2            8.  казармы17 ×3/×2/×1 по числу ратуш
3.  рынок ×1                       9.  ратуши до ×5 (при ратушах ≥ 2)
4.  мельница ×1 (повторно)        10.  казармы17 до ×8 (Россия ×6)
5.  золото ×2, железо ×1          11.  академия (казарм ≥ 2, ратуш ≥ 2)
    при onFood>20 и ратушах ≥ 2   12.  конюшня, артдепо (водные карты)
6.  уголь ×1 при iron-шахте
```

Ворота на шахты (`_ai_BuildMines`): апгрейд `food140` выполнен, `onFood > 11`,
крестьяне работают и на дереве, и на камне.

Стартовый разгон: пока крестьян < 25 и от старта < 4 минут — заказывать
`ратуши×2` крестьян (бесконечно, если еды ≥ 700).

Распределение крестьян (`_ai_ResourcesDistributionScript`):

| Нация | Дерево | Камень |
|---|---|---|
| Европа | 60% | 40% |
| Украина | 80% | 20% |
| Турция/Алжир (обычный старт) | 50% | 50% |
| Россия при казармах17 ≥ 4 | 60% | 40% |

Еда по числу крестьян: `<30 → 12`, `<45 → 21`, `<85 → 27`,
всё ×1.3 пока пикинёры не прокачаны до 3/3.

## 4. Мост

### Протокол

```
игра  ->  <каталог игры>\coss3_eco_P<n>.dat   37 полей, каждый тик ИИ
игра  <-  <каталог игры>\coss3_cmd_P<n>.dat   команды; игра читает и УДАЛЯЕТ файл
```

Удаление файла команд — это ack. **Реальный формат, снятый с живой игры:**

```
section.begin

   plind = 1

   bai = True

   gametime = 79

   food = -350
          <- инвертировано, см. 5.6
section.end

```

Имени секции нет, переводы строк CRLF, булевы как `True`/`False`.
`coss3_bridge.py` приводит их к 0/1.

### Экспортируемое состояние (37 полей)

`gametime, peacemode, peacetime_end, food, wood, stone, gold, iron, coal,
peasants, on_food, on_wood, on_stone, centers, mills, ba17, ba18, stables,
smiths, academies, markets, houses, mines_gold, mines_iron, mines_coal,
upg_century, upg_food140, upg_horse, upg_fort, upg_reaper, upg_stone200,
upg_builders, upg_wood, upg_feelds, build_slots_used, build_slots_total, plind`

### Команды

| Команда | Аргументы | Семантика |
|---|---|---|
| `BUILD` | роль, желаемое ИТОГО | 12 типов зданий, декларативно |
| `TRAIN` | роль, желаемое ИТОГО | декларативно |
| `UPGRADE` | имя | 15 апгрейдов |

Два блока, привязанные к якорям, которые не менялись с 2018 года:

## 5. Что исправлено

Мост существовал до начала работы, но **не работал ни разу**. В нём было
четыре независимых дефекта, каждого хватало, чтобы убить весь ИИ.

### 5.1 Императивный BUILD

12-ветвевая цепочка вызывала `_ai_TryUnit(..., _ai_GetUnitCount(...)+1, false)`.
Но `_ai_TryUnit` **декларативен** — четвёртый аргумент это «хочу N всего».
Повторная отправка каждый тик наращивала бы цель бесконечно.
Заменено на одну декларативную строку: `a2` = желаемое ИТОГО.

### 5.2 Ord() применялся к Boolean

```
function Ord(const val: String): Byte
```

`Ord` принимает строку. Во вставке он стоял на булевых значениях 12 раз
(`Ord(bai)`, `Ord(_ai_UpgradeIsDoneById(...))` и т.д.).
Во всех родных скриптах игры `Ord` встречается только как `Ord('R')`, `Ord('U')`.
Заменено на `ParserSetBoolValueByKeyByHandle`.

### 5.3 Незащищённое чтение апгрейдов

```pascal
function _ai_UpgradeIsDoneById(plind, cid, aiupgrade : Integer) : Boolean;
begin
   var id : Integer = gPlayer[plind].aidata.upgradeid[cid][aiupgrade];
   Result := gPlayer[plInd].upgstate[cid][id].done;   // id не проверяется
end;
```

`upgradeid` = **-1**, если у нации нет такого апгрейда, тогда `upgstate[cid][-1]`
выходит за границы массива. Экспорт звал эту функцию 9 раз подряд.
Заменено на явную проверку `if (brupgid >= 0)`.
То же самое в импорте: `_ai_TryUpgrade` индексирует `gCountry[cid].upgrade[id]`
без проверки, а команду мог прислать бот — там теперь резолв имени, потом проверка.

### 5.4 Переменная вне области видимости (корневая)

```pascal
if ParserLoadFromFileByHandle(hcmd, brcmdpath) then
begin
   var brcmdcount : Integer = ...;    // объявлена здесь
   ...
end;
Log('... ' + IntToStr(brcmdcount) + ' ...');   // использована снаружи
```

Ошибка **компиляции**, а не рантайма — поэтому секция падала целиком даже когда
файла команд не существовало и тело импорта не выполнялось. Объявление поднято
во внешний блок.

### 5.5 Работа с парсером не по идиоме игры

Вставка звала `ParserCreate('br_state')` с одним именем каждый тик и освобождала
хэндл. Игра так не делает никогда — её помощник `_parser_ParserTemporary`:

```pascal
Result := ParserSelectByKey(name);
if (Result=0) then Result := ParserCreate(name)
else if (bClear) then ParserClearByHandle(Result);
```

Переписано по этой идиоме, `ParserFreeByHandle` убран.

### 5.6 Ресурсы хранятся инвертированными

Значения приходили отрицательными: `food = -350`, `coal = -1001`.
Игра хранит ресурсы побитово инвертированными и читает через `not`:

```pascal
if (not gPlayer[plind].res[gc_resource_type_food] < 700)
```

`not(-350) = 349`, `not(-1001) = 1000`. В блок состояния добавлен `not`.

### Мои неверные выводы по ходу работы

Фиксирую, чтобы не повторять:

- **«`GetAppSaveDirectoryPath` не существует»** — существует, используется в
  `scripts/resource.script`. Дамп сигнатур из `strings cossacks.exe` неполон,
  полагаться на него как на доказательство отсутствия нельзя.
- **«`not X < Y` означает X >= Y»** — нет, это разворот инвертированного значения.
- **«окна нет»** — вывод сделан по скриншотам `screencapture` из процесса без
  разрешения Screen Recording; такие снимки содержат только обои.

- **Round-trip инжектора**: чистый → установка → reinstall → uninstall

## 6a. Куда пишет сам движок

`GetAppSaveDirectoryPath` на тестовой машине разворачивается в
`C:\Users\<user>\OneDrive\Documents\cossacks\` — там лежат `resource.lib`
и `mods.restore`. Мост туда **не** пишет намеренно: папка синхронизируется
OneDrive, а состояние переписывается несколько раз в секунду. Используется
отдельный каталог `~\coss3-io`, путь подставляется при установке через `--outdir`.

Папка игры в `Program Files` для записи недоступна: за 4.5 минуты боя игра не
изменила там ни одного файла из 20915.

## 7. Как писать бота

Команды **декларативны**: `build("center", 4)` значит «хочу всего 4 ратуши»,
а не «построй ещё одну». Игра выполнит цель, когда хватит ресурсов, и молча
проигнорирует, когда не хватает — `_ai_TryUnit` проверяет `_unit_CanApplyCostByID`.

Отсюда главное правило: **цель нужно удерживать**, переотправляя каждый тик,
а не слать один раз.

```python
import os
from coss3_bridge import Bridge, build, train, upgrade

br = Bridge(os.path.expanduser("~/coss3-io"), plind=1)
while True:
    s = br.wait_state()
    plan = [train("peasant", 30)]
    if s["mills"] < 1:            plan.append(build("mill", 1))
    if s["centers"] < 2:          plan.append(build("center", 2))
    if s["ba17"] < 2:             plan.append(build("ba17", 2))
    if br.send(plan):
        br.wait_consumed()
```

Номер `plind` — тот слот, где `bai = 1`; `send_test.py` находит его сам.

### Как убедиться, что управляете именно вы

Встроенный ИИ сам стремится к двум ратушам — это его штатный билд-ордер
(раздел 3). Поэтому вторая ратуша ничего не доказывает. Просите то, чего он
на этом этапе не планирует, например `build("center", 4)`.

### Что ещё не сделано

1. Значения `gc_resource_type_*` для `SET_RES` — движковые константы,
   в скриптах не объявлены. `BUILD`/`TRAIN`/`UPGRADE` работают без них.
2. `on_food`/`on_wood`/`on_stone` читаются до того, как
   `_ai_CalculateCurrentResourceCollection` их посчитает в этом тике —
   значения отстают на тик. Для макро-логики несущественно.
3. Военная часть: `progresswarai.inc` мостом не охвачен вовсе.

## 8. Ловушки

- **Steam вернёт оригинал.** «Проверить целостность файлов игры» снесёт мост
  молча. Автообновление — то же самое. Поставьте «Обновлять только при запуске».
- **Мультиплеер отпадает.** В игре есть проверка контрольной суммы скриптов,
  игроки отключаются (`locale/needloc/new.txt:991`).
- **`plind`.** Номер в имени файла — индекс игрока. Сверяйте с полем `plind`
  внутри состояния.
- **Ленивая инициализация.** Пока `aidata.centerfound = false`, вместо обычного
  цикла идёт `_ai_FindCenter` + `_ai_InitInitialLists`. Первые тики эпизода —
  невалидные наблюдения, пропускайте.
- **Гонка на файле команд.** Игра делает `IsFileExists` → `Load` → `Delete`.
  Писать только атомарно (`os.replace`), иначе она прочитает половину файла.
  В `coss3_bridge.py` это уже сделано.
- **`patch.txt`** в `data/scripts/` — список файлов, изменённых в каждом патче
  игры. По нему видно, придётся ли перемёрживать мост после обновления.

## 9. Карта (v2, 09.09.2026)

До этого модель видела только свою бухгалтерию: ресурсы, постройки, апгрейды.
Ни где она стоит, ни что вокруг, ни кто рядом. Добавлено в блок состояния.

### Что добавлено

Три слоя мини-карты 16x16 (мир делится на клетки, колонка 0 — запад, строка 0 —
север; клетка на карте 1024x1024 — это 64x64 игровых единицы):

| слой | где | символы |
|---|---|---|
| местность | `rrow{y}` в `coss3_map_P<n>.dat` | `#` густой лес, `+` редкий, `S` камень, `G`/`I`/`C` свободная залежь, `x` залежь под шахтой |
| базы | `brow{y}` в состоянии | `H` мой центр, `b` моё, `a` союзник, `e` враг |
| войска | `frow{y}` в состоянии | 1–9, сила вражеской армии в клетке (сила div 50) |

Числом: геометрия и своя клетка (`map_w`, `map_h`, `grid_n`, `my_x/my_z`,
`my_cx/my_cy`, `my_zone`, `zones_total`); накопленная добыча `tot_food…tot_coal`;
залежи (`ore_gold_dist`, `ore_gold_near`, …); угроза (`en_armies`,
`en_force_total`, `en_force_max`, `en_towers`, `en_near_*`, четыре сильнейшие
армии `a0_…a3_` с составом и клеткой, `danger_home`, `attract_home`,
`last_attack_ago`); свои войска (`my_units`, `my_armies`, `my_defenders`,
`my_guards`, `my_agressors`, `my_freewar`, `mil_inf/shooters/cav/art`,
`my_towers`, `my_stores`, `my_buildings`, `my_damaged`); таблица игроков
(`players`, `my_team`, `p{n}_team/cid/ai/enemy/units/bldgs`).

В map-файле дополнительно: `wood_slots_near/free`, `stone_slots_near/free`,
`wood_dist_cells` (окно 10 ячеек ресурсной сетки вокруг центра),
`ore_free_gold/iron/coal` и до восьми ближайших свободных залежей
`o{k}_res/dist/cx/cy`.

### Откуда данные

Всё из структур, которыми пользуется штатный ИИ, без новых движковых вызовов:

| данные | источник |
|---|---|
| вражеские армии, башни | `_misc_GetPlayerEnemyInfo(plind)` -> `TEnemyInfo.armyInfos` (`TArmyInfo`: infantry/shooters/cavalry/cannons/mortars/mcannons/force + bbox в scan-сетке, `_misc_ScanGridIndicesToPos` переводит в мир) |
| опасность зоны | `TopologyGetZoneBufferByIndex` -> `TTopZone.danger[pl]`, `.attract[pl]` |
| залежи | `aidata.orelist` (заполняется на инициализации, отсортирован по расстоянию до центра); занятость — `_misc_MakeListObjectsInRadius` с маской зданий, как в `_ai_GetClosestOrePlaceWithRes` |
| лес и камень | `gResGrid[i,j].fResCount[res]` и `fWorkerCount[pl][res]`, ёмкость = штуки * `gc_gameplay_resource_maxattackers_*` |
| скорость добычи | `stat.restotal[res]` — обычный счётчик, **не инвертирован** (`readtraderesources.inc:33` просто прибавляет), в отличие от `res[]` |
| базы всех игроков | `gPlayer[i].lists.buildings` + `GetGameObjectPositionXByHandle` |

### Два решения, которые стоит помнить

**Тяжёлый слой отделён.** Местность требует полного обхода `gResGrid`
(`countx * county` ячеек). Он вынесен в отдельный файл `coss3_map_P<n>.dat` и
пересобирается не чаще раза в 20 игровых секунд; всё остальное пишется каждый
тик в файл состояния.

**Таймер без нового глобала.** Первая версия хранила время последней сборки в
`global gBridgeMapTime` в `lib/classes.script` — это второй патченный файл,
который пришлось бы ставить и снимать. Отброшено. `progressTick` тоже не
годится: он тикает в `Progress`, а экономический ИИ вызывается по своему
таймеру (`_player_CheckProgressLastTimeAndIncrease(lastprogressaitime, ...)`),
так что `progressTick mod N = 0` может не совпасть ни разу. Итог: именованный
парсер живёт между тиками, поэтому таймером служит его собственное поле
`gametime` — `ParserSelectByKey('br_map_P<n>')`, сравнить, при необходимости
пересобрать. Ноль новых файлов, ноль новых глобалов.

### Ограничения

- Данные по врагу — те же, что у штатного ИИ (`TEnemyInfo` строится обходом
  объектов всех игроков), то есть **без тумана войны**. Это не подглядывание
  сверх того, что делает нативный ИИ, но и не честная разведка.
- Слой карты пишется только для ИИ-игроков и только когда
  `aidata.centerfound` — на первых тиках эпизода полей карты в состоянии нет.
- Клетка 1/16 карты грубая: армия отмечается одной клеткой по центру своего
  bbox, вражеская база и стоящая в ней армия видны в разных слоях.
- `BUILD` расширен до 14 ролей: добавлены `store` (7) и `tower` (13). Обе роли
  штатно используются самим ИИ через `_ai_TryUnit` (`store` — 4 вызова,
  `tower` — 2), проходят по общей ветке идей и подчиняются той же декларативной
  семантике. **Точку ставит игра**: `_ai_ProcessConstruction` выбирает место
  рядом с базой, задать направление командой нельзя — только количество.

### Проверено на живой игре (09.09, Steam, карта 256x256, 1 ИИ против человека)

Вставка **компилируется и работает**: пишутся оба файла, поля согласованы между
собой — `my_cx/my_cy` совпадает с `H` в слое баз, армия из `a0_cx/cy` стоит в той
же клетке, что цифра в слое войск, расстояние до неё сходится с геометрией карты.
Найдены две проблемы, обе исправлены/учтены:

- **`TPlayer.unitcount` никем не заполняется.** Ни один скрипт в него не пишет,
  движок тоже — на живой игре 0 у всех игроков при 19 крестьянах у меня.
  Заменено на `GetPlayerGameObjectsCountByHandle(GetPlayerHandleByIndex(n))`,
  ключи переименованы в `my_objects` / `p{n}_objects` (юниты + здания).
- **`tot_*` = 0 на 45-й секунде — ложная тревога.** На 246-й секунде
  `tot_food = 5508`, `tot_wood = 1092`: движок ведёт `stat.restotal` сам, а нули
  в начале честные — крестьяне ещё не донесли первый груз. Поля остаются,
  скорость добычи считается по их дельтам. `net_change` (дельта запаса) оставлен
  запасным вариантом на случай, если счётчик где-то не заполнен.

Заодно подтвердилось, что слой залежей живой: построенная шахта переводит
клетку из `C` в `x`, а `ore_free_coal` уменьшается на единицу.

## Приложение. Тупик: Wine на Apple Silicon

Пробовали поднять игру на macOS (M4 Pro, arm64) — **не получилось**, ветка закрыта.
Записано, чтобы не повторять.

Что заработало: Wine 11.0 портативно (каски Homebrew отключены с 01.09.2026 —
не проходят Gatekeeper, но каск ссылается на `tar.xz`, скачивается напрямую,
sha256 сходится). **32-битные Windows-приложения на Apple Silicon работают** —
сборка содержит полный new WoW64, 812 i386-модулей, 32-битный notepad живёт
нормально. DXVK 1.10.3 поднимается: D3D9 → Vulkan → MoltenVK → Metal, видит
M4 Pro, Vulkan 1.1.334.

Что не заработало: `cossacks.exe` и `config.exe` крутятся на 100% CPU с плоским
RSS 17-21 МБ и не создают окна. Исключено: OpenGL (обойдён через DXVK),
мост и патч (A/B с чистым оригиналом — то же самое), WoW64 и `winemac.drv`
(32-битный notepad работает: 1.5% CPU, 83 МБ). Похоже на калибровочный цикл
рантайма под Rosetta.

Отдельная методическая ошибка: скриншоты через `screencapture` из процесса без
разрешения Screen Recording возвращают **только обои** — окна приложений в кадр
не попадают. Часть выводов «окна нет» была сделана на этих пустых снимках и
оказалась неверной.

## 10. Петля эпизодов (09.09.2026, проверено на живой игре)

Эпизоды запускаются без человека. Дорога к этому вышла кривая, поэтому важны
не столько итоговые тридцать строк кода, сколько четыре факта о движке.

### Что работает

Блок в `data/scripts/units/global.inc/progress.inc` (состояние `Progress`,
исполняется для каждого игрока каждый тик), активен только для интерфейсного
игрока — `plind = GetPlayerIndexInterfaceIO`:

| команда | что делает | проверено |
|---|---|---|
| пульс | пишет `coss3_hb.dat` раз в 5 реальных секунд | да |
| `END` | `gPlayer[plind].victorystate := gc_player_victorystate_lose` | да, на экране «ПОРАЖЕНИЕ!» |
| `NEW` | `GUIExecuteState('DoNewGame')` | да, посреди боя начинается новая партия |

Протокол: `coss3_ctl.dat` (команда) → `coss3_ack.dat` (квитанция).
Клиент: `br.control('NEW')`, `python send.py --new`, раннер `run_episodes.py`.

### Четыре факта, добытые бисекцией

**1. В интерфейсном акторе не компилируется чтение файлов.** Зонд, который
только писал (`ParserSaveToFileByHandle`), работал; как только добавились
`IsFileExists`, `ParserLoadFromFileByHandle`, `DeleteFileStream` — состояние
`DoProgress` умирало целиком, без единого признака жизни. Запись при этом
работает. Отсюда правило: **любой файловый ввод — только на игровой стороне.**

**2. До интерфейса можно дотянуться из игровой стороны.** `GUIExecuteState(state)`
вызывается из библиотек, которыми пользуется игровой код
(`lib/miscext3.script:180`), и работает: `GUIExecuteState('DoNewGame')` посреди
боя запускает новую партию.

**3. Сдача морозит петлю вместе с игрой.** `doprogress.inc:546`, увидев
`victorystate <> none`, делает `SetProgressingPauseMode(True)`. Симуляция встаёт,
а блок живёт внутри неё — команды больше не читаются, перезапуститься некому.
Поэтому **эпизод завершается не сдачей, а сразу новой партией**: пауза не
возникает. `END` осталась отдельной командой для экспериментов.

**4. Фиксированные сиды так не сделать.** `DoNewGame` перегенерирует ключ карты,
если не поднят `gbool_gui_donewgamerestart`, а этот флаг объявлен внутри
интерфейсного актора и с игровой стороны не виден. Для стенда оценки
(раздел 9 плана обучения) придётся искать другой путь — вероятно, задавать
`gMap.settings.gen.randkey0/1` прямо перед вызовом и проверять, переживают ли
они генерацию.

### Диагностика, которая себя окупила

- **Пульс.** Файл, который блок пишет сам по себе, без рукопожатия. Отличает
  «блок не скомпилировался» от «блок жив, но команда не дошла» — без него
  бисекция была бы вслепую.
- **Квитанция.** `coss3_ack.dat` с полем `done`: видно, какую ветку блок прошёл.
- **`--min-loop` и `--loop 1|2|3`.** Установщик умеет ставить урезанные версии
  блока; так за два перезапуска игры нашлось, что ломается именно файловый ввод.
- **Уборка залежавшейся команды.** Если `coss3_ctl.dat` лежит дольше 15 секунд —
  его никто не читает, и клиент теперь говорит это прямо, а не «предыдущая
  команда не забрана».
