# Задание: от поручения до раздела назад

Работа в проекте почти всегда приходит ПОРУЧЕНИЕМ, а не вопросом: мак пишет
раздел в `ПЛАН.md` («МАК → WINDOWS»), игрок повторяет его в чате короткой
строкой, меры лежат в поле `что` идеи. Задание выполнено не тогда, когда прогон
отыграл, а когда ответ лёг разделом назад и числа попали в четыре файла.

Этот скилл — про порядок. Как поднять контейнер, рассказывает `coss3-farm`; как
считать результат — `coss3-results`; как править мост — `coss3-human-bot`. Здесь
то, что их связывает, и ловушки, которые съедают именно задания.

## Шаг 1. Найти задание целиком. Строка в чате — не всё задание

Короткое сообщение игрока («проверь в контейнере, идея такая-то, контроль
такой») — это ВЫЖИМКА. Полное задание в трёх местах, и читать надо все три:

```bash
cd <репозиторий> && git pull --ff-only
grep -n "МАК → WINDOWS" ПЛАН.md | head -3
grep -n "<идея>" -A 8 docker/experiments.ini
```

| где | что оттуда берётся |
|---|---|
| верхний раздел `ПЛАН.md` | зачем правка, что именно поменялось, задание дословно |
| поле `что` идеи | **меры**, и только они считаются результатом |
| поля `флаги`, `ref`, `копий`, `база` | чем прогон отличается от базы |
| строка игрока в чате | контрольные числа и что он хочет увидеть первым |

**Числа из задания выписать себе сразу** — SHA моста, три числа блоков,
`progress.inc`. Это и есть пред-пусковой контроль; без него прогон проверяет не
то, и так уже бывало.

## Шаг 2. Понять, какого рода задание. Их три, и они не взаимозаменяемы

| род | признак | где исполняется | чем |
|---|---|---|---|
| **контейнерное** | «тест-контейнер», «идея заведена», «две копии» | WSL, docker | `coss3-farm` |
| **живой игрой** | «установка, пульс, партия», «нация», «слово игрока» | Windows, открытая игра | `coss3-human-bot` |
| **только python** | «селфтест», «разбор», «посчитай» | где угодно | — |

Путать дорого: `.inc` в контейнере НЕ проверяют (цикл три минуты, экран чёрный,
«ПУЛЬСА НЕТ» имеет три причины), а идею на многих копиях в живой игре не
замеряют. Если задание требует открытой игры — **это работа игрока, и без его
слова она не начинается.**

## Шаг 3. Пред-пусковой контроль. Пять проверок, и каждая однажды обманула

```bash
git log --oneline -1
git log --oneline -1 verified
git rev-list --count verified..master
PYTHONIOENCODING=utf-8 python verify_blocks.py "<папка игры>" block_hcmd.inc block_hstate.inc block_gameloop.inc
```

**`verify_blocks.py` без имён файлов молчит и отдаёт 0.** `all([])` это `True`:
пустой вывод и «успех» означают, что не проверено НИЧЕГО. Проверка годится
только с тремя именами блоков — тогда она печатает три строки с числами.

**ПЕРВЫЙ аргумент — ПАПКА ИГРЫ, и пропустить её хуже, чем забыть файлы.** Тогда
первое имя блока съедается как папка: проверяются только ОСТАЛЬНЫЕ файлы, а
`cossacks.exe` не читается — и на каждое движковое имя печатается «нет в данных
игры», приговор «СТОП» и код 1. Выглядит как сломанный блок, а сломан вызов.
Признак — строка `~ cossacks.exe не прочитан` в самом верху и на одну строку с
числами меньше, чем файлов в команде (3.11: позвал тремя файлами по букве
скилла, получил «СТОП» на двух из трёх).

**Числа блоков смотреть у ТОГО файла, о котором говорите.** `wc -l` в
репозитории даёт на единицу меньше, чем числа задания (в блоках нет последнего
перевода строки) — это нормально. А установленный в игру файл читать питоном, а
не `ls`/`wc` через оболочку: кэш каталога Program Files уже раз отдал старое
содержимое и стоил ложного приговора «блок не пишет вовсе».

**Батарея — одной строкой, и 167 из 168 это норма:**

```bash
export PYTHONIOENCODING=utf-8; f=""; for t in selftest*.py; do python "$t" >/dev/null 2>&1 || f="$f $t"; done; echo "падает:$f"
```

Падает только `selftest.py` — ему нужны живые файлы игры. Упало что-то ещё —
задание не начинается, пока это не названо маку.

## Шаг 4. Сверить, что отличие от базы РОВНО ОДНО. Это обязанность исполнителя

Идея обещает «проверяется только изменение блока» — проверьте это сами, потому
что обещание даётся в день заведения, а прогон идёт позже:

```bash
git log --oneline --date=short --format='%h %ad %s' -4 -- <файл стратегии идеи>
```

Если файл стратегии или флаги менялись ПОСЛЕ прогона базы, отличий больше
одного, и тогда:

* прогон всё равно делается — он даёт числа;
* но в отчёте плечо называется честно: «блок **плюс** такие-то ключи python»;
* и предлагается, чем их отделить (у блока есть выключатель, у ключа — ноль).

30.10 это ровно и случилось: вместе с рефлексом обороны в файл стратегии пришли
ворота `без_атаки_до` и три ключа §170ж, и перевёрнутый размен нельзя было
приписать блоку одному.

## Шаг 5. Снять меры. По порядку поля «что», и ни одной лишней

Мера называется ДО прогона. Мерить после прогона другим числом — это новая идея,
а не результат этой. У каждой меры один из четырёх итогов, и третий с четвёртым
честнее двух первых:

* **ВЗЯТА** — с числом;
* **ПРОВАЛЕНА** — с числом;
* **НЕ СУДИЛАСЬ** — условие не сложилось (в партии не было того, что мера
  смотрит). Не вина правки;
* **НЕГОДНА ПО ПОСТРОЕНИЮ** — мера не могла сработать в принципе (например,
  строка печатается только при команде, которой в этой партии не бывает). Это
  находка про прибор, и её возвращают маку вместе с заменой.

Где что лежит — чтобы не получить ложный ноль:

| что ищем | где лежит | чего НЕ делать |
|---|---|---|
| поля состояния (`defend_on`, `my_held`) | `coss3_snap.jsonl` — полный снимок | не искать в трассе: её `state` это 16 полей, остального там нет вовсе |
| такты, команды, `why`, уроки | `coss3_bot.jsonl` | не считать по `policy.log` — он обрезан до 400 строк |
| строки блока (`DEFENCE`, `roll cleaned`, `attack skipped`) | `мост_в_игре.log` архива | `game.log` в архиве — это лог УСТАНОВКИ, 37 строк. Собственный лог игры лежит в `/opt/cossacks/log/*.log` ВНУТРИ контейнера и умирает вместе с ним |
| потери | последнее значение партии | не складывать по тактам: это счёт с начала партии |

**Поэтому: что нужно из контейнера — снять ДО того, как гасить.** Контейнер
гасят после строки `отправлено: results/...`, и всё, чего нет на томе и в
архиве, исчезает вместе с ним.

**Прежде чем объявить «этого не было ни разу»** — посчитать, пишется ли это
вообще: `grep -c <поле>` по всем файлам прогона. Ноль по полю, которого нет, —
артефакт, а не находка.

**Прежде чем назвать расхождение двух приборов поломкой** — прочитать, ЧТО
каждый считает. 30.10 «блок молчал при его 36 в четырёх клетках» объяснилось
тем, что блок считает евклидов круг, а python — клетки по Чебышёву, и четыре
клетки по диагонали это 5,6 радиуса.

## Шаг 5а. Прибор времени и прибор приказа. Оба однажды соврали в один день

**В логе игры времени НЕТ.** Префикс `LOG|N` — это НОМЕР СТРОКИ, а не секунды и не такты. Любой вывод вида «это случилось
до рубежа» по нему — догадка.

**Приказы `ATTACK` в `cmds` трассы не попадают вовсе** (ноль даже в партиях, где их было четырнадцать). Поле `attack` —
это то, что СПРОСИЛИ, и с шагом `--every` (обычно 5 с), а не то, что получила игра. Единственная запись полученного —
строки `bridge-human: ATTACK` в логе игры, и у них нет времени (см. выше).

Отсюда порядок, когда мера звучит «до такой-то секунды»:

1. **Найти якорь, сверяемый со снимками.** Годится событие, которое есть и в логе игры, и в снимке с `gametime`: строка
   `DEFENCE` против `defend_on` 1, `roll cleaned` против первого роста `my_mil_lost`, постройка против `ba17` 1 → 2.
2. **Считать плотность лога между соседними якорями** — она НЕ постоянна (5–10 строк в секунду в бою и втрое меньше в
   тишине). Экстраполяция на сотни строк назад даёт разброс в полторы минуты.
3. **Если разброс накрывает рубеж — так и сказать: «прибором не разрешается».** Это честный итог, и он лучше
   уверенного числа.
4. **НЕ строить часы по команде «раз в N секунд», не проверив.** 30.10 часы по `DEFEND` (14 строк, «раз в 60 с») соврали
   на 80 секунд: 14 меток на 906-секундную партию не ложатся.

**И просьба, которая закрывает весь класс: игровое время в строки `bridge-human:`.** Блок знает `GetGameTime`.

## Шаг 5б. Отпечаток или совпадение: проверять ВЫКЛЮЧЕННЫМ плечом

Мера «сигнал X поднялся в тот же такт, что правка сработала» ничего не доказывает, пока не проверено, что **без правки он
не поднимается**. 30.10: `squad_hunt` 0 → 1 ровно на такте включения рефлекса выглядел доказательством — а в плече с
выключенным рефлексом он тоже 1 при той же стоянке врага, потому что его поднимает совсем другое правило. Вывод снят.

Поэтому: **если идея даёт плечо A/B — сначала смотреть «выкл»**, и только потом верить отпечаткам в «вкл».
И обратное тоже: мера, которую плечо «выкл» проваливает, может быть находкой про прибор, а не про выключатель.

## Шаг 6. Отчитаться. Четыре файла

| куда | что |
|---|---|
| **`ПЛАН.md`**, новым разделом СВЕРХУ | `## WINDOWS → МАК, <дата>: <итог одной строкой>` — контроль, таблица мер, оговорки, что просим дальше |
| **`docker/experiments.ini`** | строка `итог = ...` в секцию идеи: контроль, все меры с числами, оговорки, архивы |
| **`WORKLOG.md`**, в конец | те же числа и ХОД разбора, включая ловушки, в которые попал сам |
| **`RESUME.md`** | состояние: где `master`, где метка, что стоит в игре, что осталось непроверенным |

Правила раздела, выведенные из того, как мак на них отвечает:

1. **Итог — в заголовок, числами.** Не «прогон прошёл», а «размен 74:41 и 36:8
   против 97:193».
2. **Контроль до ожидания — первым абзацем.** Мак читает его, чтобы понять,
   считать ли дальше вообще.
3. **Таблица мер строкой на меру**, каждая с одним из четырёх итогов шага 5.
4. **Оговорки не прячутся.** «Отличие не одно», «мера негодна», «аномалия
   воспроизвестись не могла» — это самое ценное в отчёте.
5. **Вопросы назад — списком в конце**, по одному на решение.

Коммит одной строкой с тем же итогом, и `git push`.

## Шаг 7. Метка `verified` — чужая. Её двигает живая игра и слово игрока

Контейнерный прогон метку НЕ двигает никогда, даже если всё взято: ферма берёт
мост по метке, и метка защищает её от моста, который не компилируется в игре.
Менялся `.inc` — метка ждёт живой игры на Windows и слова игрока. В разделе это
пишется явной строкой: «метку не двигал, проверка контейнерная».

## Чего в задании делать НЕ надо

* **не ставить мост в игру и не запускать игру без слова игрока** — живая партия
  это его работа и его время;
* **не менять `.inc` своей рукой**, если задание про проверку: правка моста идёт
  отдельным скиллом и отдельным кругом;
* **не досматривать прогон после того, как мера ответила** — модель тратит
  токены, а партия с перебитыми флагами в сравнение всё равно не пойдёт;
* **не чинить найденный дефект посреди серии** — с момента находки серия меряет
  дефект, а не идею. Гасить, починить, начать заново;
* **не писать отчёт во время живой партии игрока** — это её губит.

## Чего в заданиях ломается чаще всего (из журнала)

| что | как выглядит | что делать |
|---|---|---|
| локальный клон отстаёт | SHA задания новее `HEAD` | `git pull --ff-only` первым делом, и на Windows, и в WSL |
| идея просит `ref master`, а контейнер взял `verified` | в логе «ВНИМАНИЕ: идея просит мост …, а взят …» | при `docker run` ставить `-e COSS3_BRIDGE_REF=` самому: поле `ref` применяет только `exp.py` |
| образ не тот | в игре числа блоков не те | брать образ из документации (`coss3:2`), а не самый свежий по дате |
| проверка молчит и радует | пустой вывод, код 0 | искать, что эта проверка принимает аргументами |
| поле «не нашлось» | чистый ноль | шаг 5, таблица «где что лежит» |
| прибор врёт, а не мир | «блок не пишет вовсе» | сверить прибор с тем, что уже лежит рядом в архиве, ПРЕЖДЕ чем объявлять поломку |
| «часы» из команды «раз в N секунд» | число меток не делится на длину партии | строить шкалу только на якорях, сверяемых со снимками |
| счётчик реестра не нашёлся | `реестр.мера` в архиве нет | он живёт ТОЛЬКО в памяти процесса: мера по нему непроверяема, пока его не печатают в `why` или отчёт |
| прогон перезаписал прежний архив | тот же день и то же имя идеи в `results` | прежние файлы остаются в ИСТОРИИ `coss3-results` — назвать коммит в отчёте |
| кириллица в путях через оболочку | `FileNotFoundError` на файле, который есть | временные файлы звать латиницей; путь питону давать виндовый (`cygpath -w`) |
